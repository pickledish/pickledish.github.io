As I was working on Cheapskate, something was bothering me.

It was something kinda fundamentally wrong with the design, and while I realized this just a few weeks in, I tried to shrug it off. Now, though, I'm convinced it's the biggest issue with the site.

The app relies on Supabase for most of the unsexy parts of its architecture -- authentication, a SQL datastore, and two small serverless functions, all of which are bog-standard and all of which I happily handed off to be someone else's problem.

To be clear -- I love using Supabase, because I love the kind of cruft-free project that using Supabase enables. You get to write only the code that actually matters. It's fair to say that if I had to manage all those boilerplate services, I never would have started Cheapskate.

But... the _shape_ is wrong.

I don't want to own this data. This is a person's financial details! Wouldn't we all be more comfortable if Cheapskate stored it in a place I couldn't access? If that's even remotely possible, shouldn't I do my best to see if I can get the app to work this way?

Well, I really wanted to. I spent a lot of time trying. Let's dive in.

## Option 1: `localStorage`

https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage

The easiest and most normal thing to try. The browser already has a place to store per-site data! Can we just use that?

**Pro**

* Super easy and well-supported by every browser
* Accounts are unnecessary, no sign-up or sign-in required

**Con**

* Data is not durable; it all goes "poof" when someone clears their browser data
* Requires users to always use the same device (e.g. no viewing from phone)
* Sharing data with someone else is impossible

For an app whose main value proposition involves sharing data across a household and maintaining data entered over the course of years, this one seems like a total non-starter unfortunately!

## Option 2: `showDirectoryPicker`

https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker#browser_compatibility

A cool new option that lets you "mount" a folder on your machine into a web app. Like [this guy](https://steveharrison.dev/showdirectorypicker-opens-up-a-whole-new-world/), I'm super excited in general about the implications here!

**Pro**

* Still no account required, which is nice
* Actually durable this time -- the data lives in a real file on disk

**Con**

* Folks have to choose a data folder to use, would feel strange
* Multi-device is possible but would require external sync (e.g. Dropbox, iCloud)
* Sharing is even more finicky, requires going to external service + sharing the file there
* Not yet available in Safari or Firefox, yikes

The last con alone is damning (I don't use Chrome and [encourage you to also not use Chrome]()), but the others would be tough to swallow too -- they create a pretty high barrier to entry before the app could work like it's supposed to.

## Option 3: CloudKit Private Database

Now we're getting into the legitimately weird stuff; this is a service Apple runs allowing developers to store data in a user's iCloud account, 

**Pro**

* Sign-in must exist, but is easy (most people already have an Apple account?)
* This is the first option where multi-device and family sharing could be seamless

**Con**

* Would mean we must support, and can _only_ support, Apple SSO
* Requires every developer using it to have a $100-per-year Apple Developer account
* The JS library is [super out of date]() and doesn't support sharing from the web

Again, the last point makes this one an impossibility, but even if Apple decided to start maintaining the JS library again, one might argue this still wouldn't be a very good option lol.

Why do I have to choose between my web app respecting people's privacy and it, like... having basic functionality?

When I was working on [Cheapskate](), I realized after a few weeks that there was a fundamental issue. The app relies on Supabase for the unsexy parts of its architecture: authentication and a SQL datastore. All of it is bog-standard and all of it I happily handed off to be someone else's problem. To be clear, I love Supabase -- if I had to run all that boilerplate myself, I never would have made Cheapskate.

But... the _shape_ of it is wrong. I don't want to own this data. This is a person's financial details! Shouldn't that live with them, and not with me? Is it even possible to make a web app like this, with anything close to the same convenience and functionality (durable, works across devices, shareable with friends) as Supabase allows?

Well, I really wanted to. I spent a lot of time trying. Here are all the things that don't work:

* [localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage): the easiest one to try, and doesn't require user accounts, but the inability to access data across devices or share with someone else makes it a non-starter
* [showDirectoryPicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker): cool, and durable (unlike localStorage), but not yet supported by all browsers, and sharing (while possible) requires an extra service, e.g. Dropbox or iCloud
* [CloudKit Private Database](https://developer.apple.com/documentation/cloudkit/ckcontainer/privateclouddatabase): Apple's obscure BaaS! Locks us into Apple SSO, requires a $99 Apple Developer subscription, and the JS library doesn't implement sharing anyway
* [SQLite in Google Drive](): cute, but it similarly locks us into Google SSO, and I actually tried this, it was miserable to set up both as a user and a developer
* [B-Y-O-DynamoDB](): this is actually how I made [Cardi]() a few years ago! It works perfectly... other than how it is insane to ask people to log in with AWS keys lol
* [remoteStorage](https://remotestorage.io/rs.js/docs/): really cool, and the platonic ideal of this concept, but support is thin, and the spec explicitly calls out collaboration as [unsupported](https://remotestorage.io/rs.js/docs/getting-started/share-public-data.html)
* CRDT / "[local-first](https://www.inkandswitch.com/essay/local-first/)": again cool, but to my knowledge the "Firebase for CRDTs" proposed still does not exist, and it's unclear if it would even solve the privacy issue

Besides, all of these options compromise on the data model anyway, being KV or blob storage when all we really want is an API to run SQL queries. You know, like any normal app?

Argh!
