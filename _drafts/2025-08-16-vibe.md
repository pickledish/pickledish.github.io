Last week, I tried to "vibe code" something for the first time.

I've been using LLMs (usually [Claude Code]()) to help with work for a little while now, but in a very limited (and closely monitored) capacity -- asking it to give me the idiomatic version of some Typescript I've written, or having it write unit test scaffolding for me, stuff like this. I never accepted anything it wrote without reading it and understanding it first, to make sure it's more-or-less the same as what I would've written myself.

However, more and more I've been seeing folks use it in a totally different way: just giving Claude a broad high-level problem or feature request, pointing it at the codebase, turning "auto-accept edits" on, and then leaving it for an hour to go get dinner.

Crazy! This can't possibly turn out good results... right?

Well, at some point I figured it was probably best I find out for myself, and so the next time I found a problem that was a good fit for it (i.e. a self-contained project, in a language/platform I've never used before, which isn't mission critical infra, etc) -- I gave it a try.

## The Upshots

To get right to the chase:

* **It did work**! I now have a Sublime Text plugin that can use an OpenAI-compatible endpoint to generate code completions, exactly like I wanted. And anytime I had an idea for an improvement, like "don't ", all I had to do was ask, and Claude (...usually) figured it out first try, and then asked me to verify its work. All this, and I didn't touch a single line of code in that repository. To be honest, it still seems pretty magical to me.

However, hidden under that top-line victory are a significant number of asterisks:

* **...but it took a long time**. While Claude was able to stand up a technically-functional V1 in just a few minutes, my total amount of time working on it in Claude Code was several hours, for just a few hundred lines of code. It felt a lot like the old "the last 20% of the work will take 80% of the time", which is frustrating when you're the person tapping their foot waiting for it all to "just work already".
* **...and it was kind of expensive**? Those several hours weren't cheap! Claude's billing is a little opaque (what's a "cached prompt"?) and Claude Code's doubly so (it chooses to use a cheaper model... sometimes... for some things?), but it does let you know how much you spent at the end of each session. While I wasn't keeping notes, I think my total for this across a few hour-long sessions came out to $30 or so, which _is_ cheaper than a dev would've cost to do the same work... but I'd have rather ____.
* **...and it reached dead-ends often**. LLMs have a hard time knowing when to stop digging; my experience in this regard can be summed up by "if Claude doesn't get the problem solved in its first attempt (or _maybe_ two), it's never going to". I spent about an hour with it fumbling between `LAYOUT_INLINE` and `LAYOUT_BLOCK` trying to get the phantom preview to render in the right place -- it would try one, I would test it, tell Claude "it didn't work" with a screenshot, it would respond "[you're absolutely right](https://github.com/anthropics/claude-code/issues/3382)", and then try the other, pretty much indefinitely.
* **...and it REQUIRED examples**. In the end, the only way I was able to get Claude out of that CSS-rendering failure loop was to point it (again) at the source of [LSP-copilot](), a Sublime Text plugin which handles the same problem correctly. After seeing a working example, it was able to sort out the problem on its first try -- but I don't know if we ever would've gotten there without the example.

And the most important caveat of all:

* **I still had to understand the code**. There were a number of times Claude tried to take an objectively stupid shortcut to get around a problem, like trying to [figure out LLM stream response is done by waiting 1s for no input (which would've added 1s delay to all completions) instead of correctly parsing the end marker]. If I didn't know how to program, and wasn't at least _glancing_ at the solutions it was implementing as it went along, ____.

## Some Tips

During this process, ____, which I'll just drop in a little bulleted list here in case it can save anyone else a few minutes (or in Claude Code's case, a few dollars):

* Give it several examples upfront that cover what you want it to accomplish
* Tell it to write unit tests for the desired behavior _before_ the implementation
* Make sure it includes an absurd number of debug logs, and feed them back to the LLM
* Try with no context
* Throw it all away if you spend a little while trying to fix a problem and no dice

## The Future

Now that I have one Claude-Coded project under my belt, will I do any more vibe coding?

For now, my answer is "almost definitely not".

I learned a ton from doing this. [sentence about of course / people weren't lying / like others have said, LLMs being capable of absolute magic today compared to a few years ago.]

And more importantly, it's clear to me now that to use one of these agentic coding tools effectively requires a _distinct skill set_ from that of regular software development. There's certainly a good deal of overlap -- some may argue that you must already be a good-enough developer before you even start with these tools -- but (it seems unique enough that I'm taking those "prompt engineer" jobs a little more seriously now than I did a week ago, OR I understand now these tools have a learning curve like any other, you don't just drop in being good at them because you can speak english to them).

But despite my success, ... (not only was it kind of slow and kind of expensive, ultimately it just wasn't any fun, I got into this business because I like to know how things work, if I wanted to be a PM I would be)

And, I still have been getting a ton of value out of Claude Code, even for more directly work-related tasks, just by using it like I mentioned at the top of this post -- little code snippets, questions about the codebase, quick-and-dirty code reviews. For these use cases, Claude Code's value is instant, uncomplicated, and cheap (my average daily cost is under $1).

Either way, super excited to see where we're at a year from now.
